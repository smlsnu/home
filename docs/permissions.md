# 권한과 규칙

## 두 개의 권한 층

```
조직 역할   →  smlsnu 조직에 무엇을 할 수 있나   (Owner / Member)
저장소 권한 →  SML_SNU 저장소에 무엇을 할 수 있나 (Read / Write / ...)
저장소 규칙 →  어느 경로를 누가 고칠 수 있나      (ruleset)
```

## 조직 역할

| 역할 | 권한 |
|------|------|
| **Owner** | 조직 전체 관리. 멤버·팀·저장소 생성/삭제, 규칙 설정 |
| **Member** | 팀 소속에 따른 저장소 접근. 조직 설정 변경 불가 |

## 팀과 저장소 권한

| 팀 | 저장소 권한 | 수정 가능한 경로 |
|----|-------------|------------------|
| `lab-members` | Write | `basic_codes/`, `docs/`, 최상위 문서 |
| `project-tpw` | Write | 위 + `project_codes/tpw/` |

**Write** 권한이면 push, 브랜치 생성, PR 병합이 가능합니다. 저장소 설정 변경과 삭제는 불가능합니다.

## 저장소 규칙 (ruleset)

### main 브랜치 보호

- 브랜치 삭제 차단
- 강제 push(`--force`) 차단

### project_codes 경로 보호

`project_codes/**` 경로의 파일은 해당 프로젝트 팀만 수정·추가·삭제할 수 있습니다.
권한 없이 push하면 다음과 같이 거부됩니다.

```
remote: error: GH013: Repository rule violations found
remote: - Cannot update this protected file path
```

정상 동작이며, 필요하면 Owner에게 팀 추가를 요청하세요.

!!! note "파일 삭제는 왜 완전히 막을 수 없나요"
    Git에서 수정과 삭제는 같은 종류의 기록(커밋)입니다. 따라서 "수정은 되고 삭제만 금지"는 구조적으로 불가능합니다.
    대신 **모든 삭제가 이력에 남고 언제든 복구 가능**하며, 누가 언제 지웠는지도 추적됩니다.

## 절대 하지 말아야 할 것

- ❌ 데이터 파일 커밋 (`.pkl`, `.h5`, `.nc`, `.gz`, `.hdf`, `.he4`) — 저장소가 무거워져 못 쓰게 됩니다
- ❌ API 키·비밀번호·개인정보 하드코딩 — **이 저장소는 공개(public)입니다**
- ❌ `git push --force`
- ❌ 남의 프로젝트 폴더 임의 수정

!!! danger "키를 실수로 올렸다면"
    즉시 해당 키를 폐기(revoke)하고 Owner에게 알려 주세요.
    커밋을 되돌려도 히스토리에는 남기 때문에, 키 폐기가 유일하게 확실한 조치입니다.
